# 架構概覽

depositar AI 將網站互動、搜尋處理與資料準備分開。使用者只需透過網站提出問題；網站後端（BFF）負責暫存條件，私有搜尋 API 再協調資料檢索與本機模型。

網站後端與搜尋 API 使用 Django／Django REST Framework；HTTP view 處理請求與回應，
對話、條件與檢索邏輯由獨立的 Python 模組負責。ADRF 提供非同步 view，讓模型與
上游請求保留既有的逾時及取消行為。兩個服務共用 HTTP 基礎設定，分別維持網站
身分與私有服務憑證的存取邊界。

## 一次搜尋如何完成

**瀏覽器介面 → 網站後端 → 私有搜尋 API → 檢索服務與本機模型 → 資料集卡片**

1. 使用者輸入問題或追問。網站把本次訊息送到網站後端。
2. 網站後端取得這次搜尋的暫存條件，例如主題、涵蓋時間與格式。
3. 搜尋 API 理解本輪意圖，檢查條件是否能處理；有歧義時，先請使用者補充。
4. 搜尋 API 將同一組時間與格式條件交給 OpenSearch 的文字及向量檢索，先篩選再取候選。
5. Haystack RRF 合併兩路候選；已啟用的 reranker 接著重排，回傳資料集卡片。

這些是不同服務的責任，不要求瀏覽器直接存取模型或資料庫。

## 各部分負責什麼

| 元件 | 責任 |
| --- | --- |
| React 網站介面 | 輸入問題、顯示處理進度、條件標籤與各次搜尋結果。 |
| 網站入口與 BFF | 由 Nginx 接收網站請求；BFF 管理暫存搜尋狀態、呼叫私有 API，處理瀏覽器與 API 之間的互動。 |
| 對話搜尋 API | 理解新搜尋與追問、檢查時間及格式條件、協調檢索與排序。 |
| OpenSearch 與 Haystack | OpenSearch 保存索引並執行有界文字／向量檢索，Haystack RRF 合併候選排序。 |
| Fess 與資料準備工具 | 匯入 metadata、核對 inventory 及執行向量工作；由維護流程使用。 |
| 本機模型與 reranker | 協助判斷搜尋意圖、整理條件與重排候選資料。 |

瀏覽器呼叫網站的 `/api/session` 與 `/api/turn`；網站後端再呼叫私有的 `/v1/turn`。服務憑證由後端持有，不交給瀏覽器。

## 資料從哪裡來

資料準備流程會取得公開資料集的中繼資料，整理成目錄，再建立檢索所需的索引與向量。網站搜尋使用已準備好的資料快照，不會在每次提問時重新爬取整個資料站。

因此，搜尋結果反映的是該快照中的資訊。套用條件時，若來源資訊不足以確認條件，卡片可能會提醒使用者確認；資料是否可下載、有哪些欄位及如何使用，仍應以原始資料集頁面為準。

目前索引的重點是資料集描述與資源中繼資料。PDF／CSV 檔案內容的匯入與搜尋屬於後續功能。

## 暫存條件與入口存取

BFF 只保留本次搜尋所需的條件與待補充問題，方便下一輪追問。這不是永久對話記憶；開始新搜尋、到期或服務重新啟動後，不能依靠它恢復先前的搜尋。

需要公開存取的部署，可在網站入口使用 APISIX 與 OIDC 登入，搭配使用額度管理。是否要求登入由入口設定決定；登入身分與搜尋的暫存條件各有自己的用途。

模型、檢索服務與管理操作保留在後端邊界內。部署時應透過網站入口提供服務，詳見[部署與維護](operations.md)。

## 維護時的分工

資料更新、索引建立、模型準備與服務啟動由維護流程處理；使用者搜尋不會觸發部署或修復工作。這讓網站互動與管理操作能各自維護，也避免搜尋請求直接操作基礎設施。

想修改介面、API 或資料流程，可從[開發與文件](development.md)選擇對應入口。
